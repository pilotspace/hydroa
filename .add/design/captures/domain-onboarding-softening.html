Signature element

The rung-aware trust seal

Extends the frozen DomainStatusSeal (Badge + icon + sr-only) into a three-state climb. Member-verified is the NEW soft rung; owner-verified is the existing “sealed” state. Semantic color carries meaning; the icon + label never rely on color alone (WCAG 1.4.1).

Surface C · task invite-by-domain

Invite by domain — a domain-restricted link

“Invite your team” opens the existing InviteMemberDialog with a new mode. Because an admin can’t enumerate every mailbox at acme.com, the primitive is a shareable link scoped to @acme.com: admin-initiated (they create + share it) and domain-restricted (only @acme.com emails can redeem it) — so no stranger auto-joins.

Before the contract freezes

Design decisions to confirm

These shape the frozen contracts. My recommendation is marked; I’ll ask them as explicit choices after you’ve seen the mock.

D1 · Rung-seal visual

Three-state climb — Member-verified (azure, person) → Owner-verified (success, lock “sealed”) → Pending (warning). Recommend: as shown. Reuses the frozen seal idiom; adds only the azure member state.

D2 · Is “member-verified” persisted or derived?

Recommend: derived (signup-email domain ↔ tenant match at read time) — no `ClaimStatus` DB change, keeps the frozen pending|verified enum intact. Persist only if a task proves it load-bearing.

D3 · Invite-by-domain primitive

Recommend: a domain-restricted shareable link (admin-initiated, @domain-scoped, revocable) — scales to “the whole company” without enumerating mailboxes, and never auto-joins. Multi-email invite is the more-controlled alternative.

D4 · Auto-poll cadence & ceiling

Recommend: ~30s poll, stop after ~15 min or on tab-blur, with a manual “Check now.” Bounds client cost; the “email me when live” path covers long propagation.
