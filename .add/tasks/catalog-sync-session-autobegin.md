## CARD
goal: POST /admin/catalog/sync, the admin model routes and the /admin/teams mutations all work again for an authenticated console user, with session revocation still enforced on every one of those seams.
why: Commit `42224201` (auth-hardening P0-1) wired `ensure_session_not_revoked` into FIVE call sites. Its SELECT autobegins a transaction on whatever session it is handed; a repository that later calls `async with self._session.begin()` on that SAME session then raises `InvalidRequestError: A transaction is already begun on this Session` — a 500 on an admin route. Two of the five seams share the request session AND pair with such a repository, and both are live 500s on this branch: catalog/api/deps.py:79 -> SqlAlchemyCatalogRepository.sync_catalog (catalog/infrastructure/repository.py:67), proven by tests/catalog_sync_trigger 9/9 green at cd17ccf3 and 5/9 red at 42224201; and keys/api/deps.py:77 -> teams/api/deps.py -> SqlAlchemyTeamRepository (teams/infrastructure/repository.py:42,:209), proven by tests/teams 29 failed / 2 passed. The sibling impersonation guard did NOT trip this because it only queries for impersonation sessions; the revocation guard queries on EVERY request. The trap and its fix are already documented in this codebase at tenants/api/router.py:98-104. NOT shipped: 42224201 exists only on branch add/auth-hardening-login-sessions and is not an ancestor of origin/main, so there is no production exposure — this must simply never merge broken.

- M3 The fix closes only the read-only transaction the auth guards THEMSELVES opened — each guard records whether a transaction was already open before its read and rolls back ONLY if it began one, so a caller that already holds a transaction keeps it and no pending work can ever be discarded by a read-only guard. It never commits, and the guards' verdict semantics are untouched.
- M4 The close is in the SHARED PRIMITIVES — ALL THREE read-only guards: DbSessionRevocationGuard, DbImpersonationSessionGuard and DbUserLivenessGuard — never per-dependency, so it holds for every seam that runs them and for any future one. Closing at the dependency does NOT compose: tenants/domain/authz.py::_resolve_identity runs AFTER keys/api/deps.py::get_identity has already closed and simply re-opens a transaction, and require_active_user's liveness SELECT re-opens it again after that — both proven at runtime on POST /admin/keys. NO per-dependency rollback survives in the tree: an earlier draft kept two as "defence in depth" and a refute pass proved they actively MASK S4's sweep (an unconditional close at the dependency hides a primitive that failed to restore, so only 1 of 5 seams went red instead of 5 of 5) and contradict M3 by being unconditional where the primitive is conditional.
- M5 The restore must never displace the verdict the caller is owed: on the STORE-FAILURE branch it is best-effort (a rollback failure there is the same outage and must not turn the 503 ERR_AUTH_UNAVAILABLE into a 500), and on the SUCCESS branch it is NOT suppressed (swallowing it would leave the transaction open and silently resurrect the clash).
</must>
